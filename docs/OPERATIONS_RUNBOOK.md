# كيف تنشر الموقع وتراقبه؟

## المراقبة والتنبيهات

Workflow اسمه `Monitor production` يشتغل كل خمس دقايق. حط هذي القيم داخل GitHub Secrets:

- `PRODUCTION_MONITOR_URL`
- `OPERATIONS_ALERT_WEBHOOK_URL`

الفحص يتأكد إن الموقع والـAPI والداتا بيس والـcache والـqueue شغالين، ويراقب الأخطاء والتأخير. لو فيه مشكلة يرسل webhook ويفشّل الـworkflow.

تقدر تتحكم بالحدود من هذي المتغيرات:

- `HEALTH_MAX_ERRORS_5M`
- `HEALTH_MAX_PENDING_JOBS`
- `HEALTH_MAX_FAILED_JOBS`

## النشر

سو بيئتين محميّة في GitHub باسم `staging` و`production`، وحط فيها:

- `DEPLOY_HOST`
- `DEPLOY_USER`
- `DEPLOY_ROOT`
- `DEPLOY_URL`
- `DEPLOY_SSH_KEY`
- `DEPLOY_KNOWN_HOSTS`

شغّل `Deploy release` وحدد commit SHA أو tag ثابت. بعد اجتياز الفحوص يرفع النظام النسخة، ويغلق الموقع للصيانة، وينتظر انتهاء طلبات PHP-FPM ووظيفة الطابور الجارية قبل أخذ نسخة من قاعدة البيانات والتخزين وملف البيئة. تُحفظ النسخة الخاصة مع بصمات SHA256 داخل `<DEPLOY_ROOT>/backups`.

بعد نجاح النسخ يشغّل النظام migrations، وينقل مرفقات التدريب القديمة إلى التخزين الخاص عبر `department:secure-legacy-media --apply`، ثم يفعّل `current` ويفتح الموقع. يجب أن تعمل خدمة `momars-queue` بالأمر `queue:work` دون `--force`؛ يتوقف النشر قبل تغيير البيانات إذا تعذر إثبات انتهاء العمليات الجارية خلال مهلة الانتظار.

يحفظ النشر أيضًا بصمات سجلات الحضور قبل الترحيل وبعده أثناء الصيانة، ويتوقف قبل تفعيل النسخة إذا تغيّر أو اختفى أي سجل سابق. تحفظ ملفات `attendance-before.json` و`attendance-after.json` داخل النسخة الاحتياطية الخاصة وبصلاحيات مقيدة وتدخل في `SHA256SUMS`. يتضمن `.attendance-preservation.json` في مجلد الإصدار نتيجة المقارنة وإجماليات الدورات دون أسماء المعلمين أو أرقام دخولهم. الفحص للقراءة فقط ولا يعيد تسجيل الحضور أو يغير ساعاته.

خلك مخلي ملف البيئة بالسيرفر هنا:

`<DEPLOY_ROOT>/shared/.env`

إذا فشل النشر قبل بدء تغيير المخطط، يعيد النظام فتح النسخة السابقة. وإذا بدأ تغيير المخطط، يبقى الموقع في الصيانة ويحتفظ الملف `<DEPLOY_ROOT>/shared/deployment-recovery-required` بمسار النسخة الاحتياطية. تُكتب هذه العلامة قبل أول migration، وتبقى أيضًا عند انقطاع اتصال النشر. يحتفظ النظام بآخر خمس نسخ من الكود، وتبقى النسخ الاحتياطية مستقلة عنها.

## لو تبي ترجع نسخة قديمة

شغّل `Roll back release`، اختر البيئة، وحط SHA واحد من النسخ المحفوظة. الرجوع يبدّل الكود وبعدها يشغّل فحص staging.

الرجوع بالكود وحده مسموح فقط بين نسخ تحمل جيل المخطط نفسه. يرفض السكربت الرجوع إلى نسخة تسبق فصل الإدارات أو عند وجود علامة استعادة معلقة.

عند فشل تغيير المخطط: أبقِ الموقع في الصيانة، وتحقق من `SHA256SUMS` داخل النسخة الاحتياطية، ثم استعد قاعدة البيانات والتخزين وملف البيئة معًا، وأعد تفعيل المسار المحفوظ في `previous-release`. افحص توافق النسخة المستعادة قبل حذف علامة الاستعادة وتشغيل `artisan up`. لا تشغّل migrations عكسية ولا تفتح الكود القديم على المخطط المعدل جزئيًا.

## إنشاء حساب المدير العام

بعد نجاح النشر، أضف السر المؤقت `MOMARS_GENERAL_MANAGER_PASSWORD` إلى أسرار مستودع GitHub أو بيئة `production`، ثم شغّل `Create production general manager` برقم حساب جديد والاسم الكامل. تُمرر كلمة المرور إلى الأمر الخادمي عبر stdin دون طباعتها أو وضعها في وسائط العملية. يرفض الأمر ترقية حساب موجود أو الاستيلاء على رقم محجوز. احذف السر المؤقت بعد اكتمال الإنشاء والتحقق من الدخول.

بعد النشر أو الرجوع تأكد من هذي الروابط والأشياء:

- `/up`
- `/api/health/operations`
- الـAPI العام
- الدخول والصلاحيات
- CORS

وتقدر تشغّل الفحص كذا:

```bash
npm run verify:staging
```
